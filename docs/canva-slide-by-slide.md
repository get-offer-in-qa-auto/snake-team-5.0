# SLIDE 7

## Проблема 1. TeamCity останавливался на первом запуске

### Что произошло

На чистом runner обычного запуска Docker-контейнера оказалось недостаточно.
TeamCity требовал подтверждения first start, выбора БД, принятия лицензии,
создания администратора, access token и авторизации Agents.

### Почему это глобальная проблема

До завершения setup невозможно выполнить ни API-, ни UI-, ни DB-проверки.
Проблема блокировала весь CI-контур.

### Решение команды

Команда автоматизировала первоначальную настройку TeamCity: подтверждение первого
запуска, выбор базы данных, принятие лицензии, создание временного администратора
и ключа доступа. Перед тестами система проверяет, что TeamCity полностью настроен
и готов к работе.

### Результат

В каждом CI job автоматически разворачивается и настраивается отдельный чистый
TeamCity-стенд; ручное вмешательство не требуется.

# SLIDE 8

## Проблема 2. Параллельные тесты влияли друг на друга

### Что произошло

При параллельном запуске несколько API- и UI-тестов одновременно создавали,
изменяли и удаляли данные на одном TeamCity-стенде. Один тест мог перезаписать
или удалить данные, которые в этот момент использовал другой. Это создавало
ложные падения и делало результаты нестабильными и невалидными.

### Решение команды

- выделила отдельный чистый TeamCity-стенд для API и каждого браузера;
- изолировала тестовые данные с помощью уникальных имён и идентификаторов;
- закрепила за каждым тестом создание и удаление собственных объектов;
- согласовала количество параллельных тестов с количеством TeamCity Agents.

### Результат

Тесты выполняются параллельно, но не меняют данные друг друга. Результаты стали
стабильными и воспроизводимыми: падение указывает на реальную проблему, а не на
конфликт между одновременно работающими тестами.

внутреннем состоянии TeamCity. При этом прямое подключение к работающей HSQLDB
было небезопасным.

### T — Task

Создать единый безопасный механизм проверки данных для HSQLDB и PostgreSQL без
SQL внутри самих тестов.

### A — Action

Я разделила DB-слой на запросы, исполнители и клиент; реализовала безопасное
чтение HSQLDB через backup snapshot и read-only подключение к PostgreSQL; добавила
проверки сохранения и удаления основных сущностей и database preflight.

### R — Result

API-проверки получили независимое подтверждение на уровне базы данных. Одна
тестовая логика работает с HSQLDB и PostgreSQL, не вмешиваясь в работу TeamCity.

# SLIDE 14

## Проблема 1. Для PostgreSQL потребовался отдельный CI-стенд

### S — Situation

Основной CI-стенд запускал TeamCity со встроенной HSQLDB внутри готового
окружения. PostgreSQL требовала отдельного контейнера, собственного хранилища и
сети. Если база не успевала запуститься или TeamCity не получал JDBC-драйвер и
настройки подключения, сервер не стартовал и тесты не выполнялись.

### T — Task

Построить отдельный воспроизводимый стенд TeamCity с PostgreSQL, который можно
поднять на чистом runner без ручной настройки.

### A — Action

Я создала Docker Compose с отдельными контейнерами TeamCity Server, Agents и
PostgreSQL 17.5; добавила healthcheck базы и правильный порядок запуска;
автоматизировала установку JDBC-драйвера, подготовку Data Directory и передачу
временных credentials.

### R — Result

TeamCity с PostgreSQL автоматически разворачивается в отдельном CI-контуре.
Полный API- и UI-regression запускается вручную и по nightly-расписанию, не
увеличивая время обязательных PR-проверок.

# SLIDE 15

## Проблема 2. DB-клиент для HSQLDB не работал с PostgreSQL

### S — Situation

DB-проверки для встроенной HSQLDB читали данные из backup snapshot TeamCity.
После подключения PostgreSQL этот механизм нельзя было использовать напрямую:
внешняя база требовала отдельного соединения и другого способа выполнения
запросов. Без нового клиента тесты не могли проверять состояние PostgreSQL.

### T — Task

Добавить поддержку PostgreSQL, не дублируя DB-проверки и не добавляя SQL в сами
тесты.

### A — Action

Я разработала отдельные `PostgreSQLDatabaseClient` и `PostgreSQLExecutor`,
настроила подключение через DSN и перевела транзакции в read-only режим. Фабрика
автоматически выбирает PostgreSQL или backup adapter, а тесты используют общий
`DBRequest` и одинаковые verification steps.

### R — Result

Одни и те же DB-проверки работают с двумя источниками: HSQLDB читается через
безопасный snapshot, а PostgreSQL — через прямое read-only соединение. Тестовую
логику и SQL дублировать не пришлось.

# SLIDE 16

## Проблема 3. UI-тесты падали нестабильно

### S — Situation

Сценарий создания Build Step то проходил, то падал в браузерных прогонах.
Build Step уже создавался в TeamCity, но тест начинал следующую проверку до
завершения перехода на страницу Build Steps. Из-за нерегулярного падения
причину пришлось искать в несколько этапов.

### T — Task

Найти источник нестабильности и сделать сценарий предсказуемым без фиксированных
задержек и бесконечного увеличения timeout.

### A — Action

Я проанализировала поведение страницы после нажатия Save, уточнила фактический
URL перенаправления и добавила ожидание целевой страницы. Только после завершения
перехода тест проверяет созданный Build Step.

### R — Result

Сценарий синхронизирован с реальным состоянием TeamCity. Проверка больше не стартует
во время перехода страницы, а UI-regression использует одинаковую логику ожиданий в Chromium,
Firefox и WebKit.
