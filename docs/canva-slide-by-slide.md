# SLIDE 7

## Проблема 1. TeamCity останавливался на первом запуске

### Что произошло

На чистом runner обычного запуска Docker-контейнера оказалось недостаточно.
TeamCity требовал подтверждения first start, выбора БД, принятия лицензии,
создания администратора, access token и авторизации Agents.

### Почему это глобальная проблема

До завершения setup невозможно выполнить ни API-, ни UI-, ни DB-проверки.
Проблема блокировала весь CI-контур.

### Решение команды

Команда автоматизировала первоначальную настройку TeamCity: подтверждение первого
запуска, выбор базы данных, принятие лицензии, создание временного администратора
и ключа доступа. Перед тестами система проверяет, что TeamCity полностью настроен
и готов к работе.

### Результат

В каждом CI job автоматически разворачивается и настраивается отдельный чистый
TeamCity-стенд; ручное вмешательство не требуется.

# SLIDE 8

## Проблема 2. Параллельные тесты влияли друг на друга

### Что произошло

При параллельном запуске несколько API- и UI-тестов одновременно создавали,
изменяли и удаляли данные на одном TeamCity-стенде. Один тест мог перезаписать
или удалить данные, которые в этот момент использовал другой. Это создавало
ложные падения и делало результаты нестабильными и невалидными.

### Решение команды

- выделила отдельный чистый TeamCity-стенд для API и каждого браузера;
- изолировала тестовые данные с помощью уникальных имён и идентификаторов;
- закрепила за каждым тестом создание и удаление собственных объектов;
- согласовала количество параллельных тестов с количеством TeamCity Agents.

### Результат

Тесты выполняются параллельно, но не меняют данные друг друга. Результаты стали
стабильными и воспроизводимыми: падение указывает на реальную проблему, а не на
конфликт между одновременно работающими тестами.

# SLIDE 9

## Проблема 3. Невоспроизводимость тестового окружения

### Что произошло

Локальные запуски и запуски на чистых CI runners могли выполняться в разных
условиях. Результат зависел от версии и состояния TeamCity, настроек базы данных,
credentials, доступности Agents и готовности сервисов. Один и тот же набор тестов
мог проходить на заранее подготовленном стенде и падать после развёртывания с
нуля.

### Почему это глобальная проблема

Различия окружений влияли одновременно на API-, UI- и DB-проверки. Команда не
могла однозначно определить, связано ли падение с дефектом TeamCity, тестом или
конфигурацией стенда.

### Решение команды

Команда зафиксировала конфигурацию окружения в Docker Compose и CI actions,
централизовала параметры запуска и credentials, автоматизировала настройку
TeamCity и добавила healthcheck, preflight и проверки готовности Server, Agents и
базы данных. Для API и каждого браузера поднимается отдельный чистый стенд.

### Результат

На чистом runner воспроизводится одинаковый порядок развёртывания и настройки
окружения. Запуск больше не зависит от вручную подготовленного состояния, а
результаты разных jobs можно сравнивать между собой.

# SLIDE 16

## Проблема 2. DB-клиент для HSQLDB не работал с PostgreSQL

### S — Situation

DB-проверки для встроенной HSQLDB читали данные из backup snapshot TeamCity.
После подключения PostgreSQL этот механизм нельзя было использовать напрямую:
внешняя база требовала отдельного соединения и другого способа выполнения
запросов. Без нового клиента тесты не могли проверять состояние PostgreSQL.

### T — Task

Добавить поддержку PostgreSQL, не дублируя DB-проверки и не добавляя SQL в сами
тесты.

### A — Action

Я разработала отдельные `PostgreSQLDatabaseClient` и `PostgreSQLExecutor`,
настроила подключение через DSN и перевела транзакции в read-only режим. Фабрика
автоматически выбирает PostgreSQL или backup adapter, а тесты используют общий
`DBRequest` и одинаковые verification steps.

### R — Result

Одни и те же DB-проверки работают с двумя источниками: HSQLDB читается через
безопасный snapshot, а PostgreSQL — через прямое read-only соединение. Тестовую
логику и SQL дублировать не пришлось.

### S — Situation

Для проверки permissions UI-тесты должны были выполняться как от имени

### A — Action

пользователя и добавляет cookie в Playwright context. Для выбора сессии добавил
markers `admin_session` и `user_session`, а временное состояние пользователей
изолировал через `SessionStorage`.

### R — Result

UI-тесты могут декларативно запускаться с нужной ролью без повторения шагов
входа. Каждый сценарий получает отдельную управляемую сессию, а проверки
permissions стали короче и предсказуемее.

а оставшиеся данные влияли на повторные и параллельные запуски.

### T — Task

Подключить сущности, создаваемые через UI, к общей системе регистрации и очистки
тестовых данных.

### A — Action

Я добавил marker `entity_will_be_created`, который регистрирует модель будущей
сущности в `CreatedObjectsRegistry` до выполнения действия в браузере. Также
расширил cleanup для проектов, пользователей, access tokens и связанных
объектов.

### R — Result

Объекты, созданные через UI, автоматически удаляются после теста. Повторные
запуски начинаются без оставшихся данных, а риск конфликтов между сценариями
снизился.

# SLIDE 25

## Проблема 3. UI-проверка не подтверждала сохранение данных

### S — Situation

Сообщение об успехе или появление элемента на странице не гарантировало, что
TeamCity действительно сохранил изменения во внутреннем состоянии. UI-тест мог
пройти, даже если данные отображались временно или сохранились некорректно.

### T — Task

Добавить независимую проверку результата ключевых UI-операций.

### A — Action

получает сущность через REST API и сравнивает её с исходными данными. Созданный
access token проверяется через API, а после удаления пользователя дополнительно
подтверждается его отсутствие.

### R — Result

UI-тесты проверяют не только отображение результата в браузере, но и фактическое
состояние TeamCity. Ложноположительные результаты исключены, а место ошибки легче
определить по уровню, на котором разошлись данные.

# SLIDE 31

## Проблема 1. Server-generated ID ломал сравнение моделей

### S — Situation

После создания Build Step TeamCity самостоятельно присваивал ему идентификатор вида `RUNNER_*`. 
Этого ID не было в исходном request, поэтому универсальное сравнение request и response считало корректно созданный Build Step различающимся.

### T — Task

Понять источник расхождения и изменить проверку так, чтобы учитывать контракт TeamCity, не убирая валидацию response.

### A — Action

Я выяснил, что идентификатор Build Step принадлежит серверной стороне и не должен сравниваться с исходным request. 
Исключил `id` из общего сравнения моделей, сохранив проверку остальных переданных полей. 
Наличие корректного ID в response проверяется отдельно.

### R — Result

Тест перестал давать ложные падения на корректном поведении TeamCity. 
Проверка response не была ослаблена: клиентские поля сравниваются с request, а созданные на сервере ID валидируется отдельно.

Позитивные тесты перестали зависеть от случайных невалидных конфигураций.

# SLIDE 33

## Проблема 3. UI login test падал из-за состояния TeamCity

### S — Situation

После локального запуска TeamCity в Docker тест авторизации через UI стабильно падал. 
Контейнеры и сервер работали, поэтому первоначально причиной могли быть Playwright, селекторы, credentials или конфигурация тестового окружения.

### T — Task

Локализовать источник ошибки и добиться воспроизводимого запуска UI login test без изменения корректной тестовой логики.

### A — Action

Я последовательно проверил состояние Docker-окружения и механизм TeamCity Super User, пересоздал стенд и отделил проблему инфраструктуры от UI-теста. 
В результате выяснил, что для сценария отсутствовал обычный пользователь TeamCity. После создания администратора `admin/admin` повторно запустил тот же тест.

### R — Result

UI login test начал успешно выполняться без изменения селекторов. 
Причина была локализована на уровне подготовки окружения, а не ошибочно замаскирована изменениями в UI-автоматизации.
